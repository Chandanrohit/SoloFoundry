# Product design

> **Status:** reviewed learning path and decision guides. No specific product has been user-tested by these materials.

Product design turns evidence about a problem into an outcome people can understand and achieve. It connects what was learned in [opportunity discovery](../01-discover/README.md) to buildable scope and observable product behavior.

## A practical learning path

1. [Product brief and scope](product-brief-and-scope/README.md): define the user, outcome, evidence, constraints, and smallest useful release.
2. [Journeys and prototypes](journeys-and-prototyping/README.md): map the whole task, decide where software fits, and prototype the riskiest workflow.
3. [Usability research](usability-research/README.md): test representative tasks, observe friction, and turn findings into changes.
4. [Accessible content and design systems](accessible-content-and-design-systems/README.md): make interaction, language, and reusable patterns work for more people.

Start with the [product brief template](../templates/PRODUCT_BRIEF.md); use the [usability test plan](../templates/USABILITY_TEST_PLAN.md) to plan a prototype or service test.

## Design principles

- Design for a real user goal and context, not a feature list or internal process alone.
- Include people who may be excluded by the default device, language, environment, ability, or level of support.
- Make the normal path, edge cases, errors, recovery, privacy, and support behavior explicit.
- Test assumptions with the least costly method that still gives relevant evidence.
- Use standards and established components where they fit, while checking that they work in the actual service.
- Treat compliance claims, design-system adoption, and automated accessibility scans as insufficient substitutes for user testing and technical review.
